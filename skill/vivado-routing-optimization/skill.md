# Vivado 布线提速与收敛

目标是缩短得到可用实现结果的时间，同时保留设计身份、约束、功能和时序验收。先做只读材料盘点；只有用户明确授权构建实验后，才启动 Vivado。阅读材料时不触发构建、停止或重启现有任务、抢占资源、操作板卡或写启动介质。

## 执行规则

1. 先按 [详细工作流](references/workflow.md) 核对现有运行记录、源码/约束/DCP 身份、工具与器件版本、目标时钟、线程、内存及其他负载。进程存在或日志停更都不足以单独判定运行状态。
2. 将阶段报告分类为正在运行、已完成的阶段检查点、最终实现、失败或用户停止。迭代计数、拥塞重叠数和中间时序不能换算成完成百分比、最终状态或 ETA。
3. 只提出一个有证据的最小实验，并说明单一改动、资源预算、停止条件和验收门槛。器件、时钟、约束、工具版本及输入身份应固定；若必须变化，说明结果为何不能直接比较。
4. 若得到实验授权，在独立候选目录执行并保留运行记录。完成后按 [报告模板](assets/validation_report_template.md) 分别填写实测、推导和未知项；OOC、完整平台与实板结果分别报告。

## 诊断方向

根据证据选择一个方向，不要一次改多个变量：

- **线程与机器负载**：对照实际墙钟时间、峰值内存与结果质量。增加线程不保证线性提速；运行中的线程设置是否生效须看实际工具行为。
- **布局/布线策略**：根据局部拥塞和阶段报告选 directive 或物理优化；先用当前 Vivado 版本帮助或 AMD 文档核实选项。
- **约束和布局**：确认时钟、I/O 和路径约束完整真实；不放宽约束、不加虚假例外来制造通过。
- **检查点与增量**：核实 DCP 的阶段、工具版本、器件、源码与约束身份；无匹配检查点时不声称能续跑布线。
- **RTL 与并行度**：只有关键路径或拥塞证据支持时才改局部控制、流水、数据复用或并行度；考虑握手、数值一致性、资源、吞吐，并列明需要的功能验证。

不要把一个工程的 DSP、线程数或一次候选推广为通用结论。若路由时间与端到端吞吐目标冲突，可结合 `zynq-ps-pl-performance`，但布线速度本身不代表 FPS。

## 输出与验收

对照表至少含源码/约束及 DCP 身份、版本、配置、完整阶段墙钟耗时、峰值内存、最终布线状态、WNS/TNS、hold、脉宽、时序覆盖、资源及 DRC。保留报告路径和失败/停止状态。布线完成不等于时序通过；时序通过不等于功能正确或达到目标 FPS。未知项保持未知，不承诺未实测提速倍数。
