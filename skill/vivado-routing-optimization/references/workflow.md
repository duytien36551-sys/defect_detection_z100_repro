# 操作工作流

## 1. 固定目标和授权

记录用户关心的是总构建墙钟时间、某个实现阶段、布通率、时序余量、资源，还是性能/功能。确认当前是否仅要求分析；本技能默认只读。加载技能不授权启动或结束作业、改变约束、写入板卡、启动训练或修改持久介质。

若用户明确要求实验，先写清楚目标配置、允许改动、资源上限、独立工作目录、停止条件和验收门槛。存在其他活跃作业时，查清所有者和启动方式；不确定归属时不得终止或覆盖。

## 2. 收集基线材料

优先从工程和本机记录中查找：

- run manifest、命令行、退出码、时间戳、阶段状态及日志位置；
- Vivado 版本/build、器件、顶层、时钟和实现模式；
- RTL/网表与 XDC 源清单或 SHA256；输入 DCP 的来源、阶段、版本和 SHA256；
- 使用的策略/directive、线程、机器 CPU/内存/磁盘和同时运行的任务；
- synth/place/physopt/route 报告中的 LUT、FF、BRAM、DSP、拥塞、关键路径、route status、时序覆盖及 DRC。

把每份证据绑定到运行 ID 和检查点。若信息缺失，标为未知；先查源清单和报告，不要根据目录名、修改时间或进程名猜测设计身份或运行所有者。

## 3. 判定阶段和报告质量

用退出码、run manifest、报告和检查点交叉确认状态：

- `RUNNING`、`STOPPED_BY_USER`、失败退出与完成是不同状态；用户停止不等于工具失败。
- placement 或 physopt checkpoint 是阶段成果，不是 route 完成。
- 中间时序可能在后续阶段变化；global route 或局部拥塞不是详细布线结果。
- route 迭代次数、拥塞 overlap、log 最后更新时间不能单独转成完成百分比或可靠 ETA。
- 区分 CPU 秒和 elapsed wall time；只在同一 run 的明确定义范围内计算阶段耗时。
- OOC 与完整平台分别报告；缺失报告不能以另一个阶段的估计值补齐。

## 4. 选择单变量实验

先从报告中提出一条可证伪的假设，再选择一个改动。控制器件、时钟、RTL、XDC、Vivado 版本和输入 DCP；候选重跑时除选定变量外保持一致。新 RTL 必须作为新设计身份。记录对照方法：

| 迹象 | 可考虑的实验 | 必须保持或复核 |
| --- | --- | --- |
| CPU 饱和、内存有余量且任务争抢少 | 比较工具支持的线程数 | 墙钟、峰值内存、完成状态和时序质量；不推断线性加速 |
| 局部拥塞或高 fanout 集中 | 依据当前版本文档比较一个策略或局部布局改动 | 完整平台的布通、时序、DRC；不得只看区域拥塞颜色 |
| 关键路径约束或时钟定义可疑 | 先核对 XDC 与真实接口意图 | 禁止通过放宽目标、遗漏路径或伪造 false path 造出通过 |
| 有匹配来源和身份的有效 checkpoint | 评估阶段恢复或增量实现 | 核验工具版本、part、输入身份和实际复用记录；不可把普通恢复称为增量复用 |
| RTL 关键路径或数据互连成为瓶颈 | 仅针对证据考虑局部流水、控制、复用或并行度 | 握手/周期语义、数值一致性、资源、整图时序和必要的板级回归 |

实验开始前应有磁盘与内存余量及失败处理方案。策略名和参数以该 Vivado 版本支持情况为准；不照搬其他工程的 directive 或线程设置。

## 5. 比较并判断

逐一比较 [报告模板](../assets/validation_report_template.md) 中的身份、配置、耗时、资源与质量门槛。完整 run wall time 应来自起止时间戳或明确的整体 elapsed 字段；各阶段时间只在日志定义清楚时列出，不与 CPU 时间或其他并行任务累加。

布线性能改善至少要求输入可比、完整 route 结束并且质量门槛满足。报告 setup、hold、pulse width、时序覆盖、未布线/错误网络、关键 DRC 与 Warning 分组。若候选更快但未完成、关键质量退化或报告不全，结论是未通过或不可判定，不以较短运行时间代替验收。

性能结果不能替代功能检查或 FPS 测量。若 RTL、流水、存储映射或数据并行改变，明确列出需要的 RTL 仿真、软件/整数一致性、完整平台实现和板端验证；未运行的项目写“未运行”。

## 6. 汇报下一步

报告保留原始证据路径、来源身份、失败/停止原因及未知项。结论只回答当前范围，给出一项下一步建议和接受它所需的门槛。不复制私有大日志到技能目录；需要交付报告时只摘录必要数值和文件哈希。
